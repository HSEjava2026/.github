# Практическое задание: Разработка системы управления персоналом (HRM Lite) — Часть 4

## 1. Общее описание

**Цель задания:** Закрепить навыки работы с Spring Framework, Spring Boot, Spring Web MVC, Spring Data JPA, Liquibase и Swagger.

Вам необходимо перевести существующее консольное приложение для управления данными сотрудников компании в веб-приложение с REST API, сохранив при этом возможность работы с консолью (опционально).

**UPD: 13/05**
Основные задачи:
* Подключение приложения к БД
* Взаимодействие по RestAPI
* Подключение Swagger UI
* Адаптация сервисного слоя
* Тестирование

Опционально:
* Инициализация таблиц и данных с использованием liquibase
* Глобальный перехватчик исключений
* Оформление Swagger через @Operation
* Валидация через аннотации
---

## 2. Архитектура приложения

Проект должен содержаться в пакете `ru.hse` и быть переведен на Spring Boot с разделением на слои:

1. `model` — описание сущностей (JPA-сущности).
2. `repository` — Spring Data JPA репозитории.
3. `service` — бизнес-логика приложения.
4. `controller` — REST контроллеры.
5. `exception` — пользовательские классы исключений и глобальный обработчик ошибок.
6. `config` — конфигурационные классы (Swagger, безопасность — опционально).
7. `dto` — классы для передачи данных (Data Transfer Object).

Main class - `HRMApplication` (аннотированный `@SpringBootApplication`)

### Шаг 2(опционально): Миграции базы данных (Liquibase)

**Для реализации задачи на базовом уровне, достаточно будет реализовать JPA сущности в model. Если реализовывать эту часть задачи, то не забудьте внести изменения в `application.yml`**

В пакете `db/changelog` создайте Liquibase changelog файлы для инициализации схемы базы данных:

**Требования к миграциям:**

1. Создайте таблицу `employee` со следующими колонками:
   * `id` (BIGINT, PRIMARY KEY, AUTO_INCREMENT)
   * `name` (VARCHAR(255), NOT NULL)
   * `position` (VARCHAR(255), NOT NULL)
   * `salary` (DECIMAL(19,2), NOT NULL)

   * `grade` (VARCHAR(20)) — только для программистов

2. Создайте таблицу `task`:
   * `id` (BIGINT, PRIMARY KEY, AUTO_INCREMENT)
   * `task_name` (VARCHAR(255), NOT NULL)
   * `start_day` (DATE, NOT NULL)
   * `end_day` (DATE, NOT NULL)
   * `state` (VARCHAR(20), NOT NULL)

3. Создайте связующую таблицу `programmer_task` (многие ко многим):
   * `programmer_id` (BIGINT)

   * `manager_id` (BIGINT)

5. Создайте таблицу `user` для аутентификации (из части 3):
   * `id` (BIGINT, PRIMARY KEY, AUTO_INCREMENT)
   * `username` (VARCHAR(100), UNIQUE, NOT NULL)
   * `password` (VARCHAR(255), NOT NULL)
   * `role` (VARCHAR(30), NOT NULL)
   * `employee_id` (BIGINT, ссылается на employee.id)

6. **Засидируйте тестовые данные** (минимум 3 сотрудника, 2 задачи, 2 пользователя с разными ролями) через Liquibase (используйте теги `insert`).

### Шаг 3: JPA-сущности

Переработайте классы из `model` в JPA-сущности:

* `Employee` — абстрактный класс с аннотациями `@Entity`, `@Inheritance(strategy = InheritanceType.SINGLE_TABLE)`, `@DiscriminatorColumn`
* `Programmer` — с аннотацией `@DiscriminatorValue("PROGRAMMER")` и связью `@ManyToMany` с `Task`
* `Manager` — с аннотацией `@DiscriminatorValue("MANAGER")` и связью `@ManyToMany` с `Programmer`
* `Task` — с аннотацией `@Entity` и связью `@ManyToMany` с `Programmer` (mappedBy)
* `User` — JPA-сущность для аутентификации

**Требования:**
* Используйте `GenerationType.IDENTITY` для генерации ID
* Все связи должны быть корректно настроены (каскадные операции — на ваше усмотрение)
* Используйте `LocalDate` для дат

---

### Шаг 4: Репозитории (Spring Data JPA)

Создайте интерфейсы-репозитории в пакете `repository`:

* `EmployeeRepository` — расширяет `JpaRepository<Employee, Long>`
* `ProgrammerRepository` — расширяет `JpaRepository<Programmer, Long>`
* `ManagerRepository` — расширяет `JpaRepository<Manager, Long>`
* `TaskRepository` — расширяет `JpaRepository<Task, Long>`
* `UserRepository` — расширяет `JpaRepository<User, Long>`

**Дополнительные методы (используйте производные запросы или `@Query`):**

* `List<Programmer> findByGrade(Grade grade)`
* `List<Employee> findByHireDateBefore(LocalDate date)`
* `Optional<Employee> findByName(String name)`
* `List<Task> findByStateAndEndDayBefore(State state, LocalDate date)` — просроченные задачи

### Шаг 6: REST Контроллеры

Создайте REST контроллеры в пакете `controller`:

**EmployeeController** (базовый путь `/api/employees`):
* `GET /` — получение всех сотрудников (с возможностью фильтрации по должности)
* `GET /{id}` — получение сотрудника по ID
* `POST /` — создание нового сотрудника
* `PUT /{id}` — обновление сотрудника
* `DELETE /{id}` — удаление сотрудника
* `GET /{id}/salary` — получение зарплаты сотрудника

**ProgrammerController** (базовый путь `/api/programmers`):
* `GET /{id}/tasks` — получение всех задач программиста
* `POST /{id}/tasks` — назначить задачу программисту
* `PUT /{id}/tasks/{taskId}/complete` — отметить задачу как выполненную
* `GET /grade/{grade}` — получить всех программистов определённого грейда

**ManagerController** (базовый путь `/api/managers`):
* `GET /{id}/programmers` — получить всех программистов менеджера
* `POST /{id}/programmers/{programmerId}` — назначить программиста менеджеру

**TaskController** (базовый путь `/api/tasks`):
* `GET /` — все задачи
* `GET /overdue` — просроченные задачи
* `POST /` — создание задачи
* `PUT /{id}/state` — обновление статуса задачи

**AuthController** (базовый путь `/api/auth`):
* `POST /login` — аутентификация (возвращает токен или информацию о пользователе)
* `POST /logout` — выход
* `GET /me` — информация о текущем пользователе

**Требования:**
* Используйте соответствующие HTTP методы и коды ответов (200, 201, 400, 404, 403)
* Все методы должны принимать и возвращать DTO (не Entity)
* Обрабатывайте исключения и возвращайте понятные сообщения об ошибках

### Шаг 7 (опционально): Глобальная обработка исключений

Создайте класс `GlobalExceptionHandler` с аннотацией `@RestControllerAdvice`:

Обрабатывайте следующие исключения:
* `EmployeeNotFoundException` → 404 Not Found
* `TaskNotFoundException` → 404 Not Found
* `InvalidDataException` → 400 Bad Request
* `SecurityException` → 403 Forbidden
* `MethodArgumentNotValidException` → 400 Bad Request с детализацией ошибок валидации

Формат ответа об ошибке должен быть единообразным:
```json
{
  "timestamp": "2024-01-15T14:30:25",
  "status": 404,
  "error": "Not Found",
  "message": "Employee with id 123 not found",
  "path": "/api/employees/123"
}
```

## 4. Функциональные требования

1. Приложение должно запускаться как Spring Boot приложение.
2. База данных H2 должна быть доступна в памяти или на диске (настройте `application.yml` или `application.properties`).
3. Liquibase должен применять миграции при каждом запуске.*
4. Swagger UI должен позволять тестировать все эндпоинты API.
5. Все CRUD операции над сущностями должны быть реализованы через REST API.
6. Коды ответов HTTP должны соответствовать семантике REST.
7. Существующая консоль (из частей 2-3) может быть сохранена, но должна работать параллельно с веб-сервером (в отдельном потоке или через `CommandLineRunner`).
8. При любых ошибках валидации или бизнес-логики клиент должен получать понятное сообщение с соответствующим HTTP статусом.
